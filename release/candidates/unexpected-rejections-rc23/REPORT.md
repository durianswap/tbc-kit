# rc.23：异常拒绝与同类型问题修复报告

## 结论与范围

JS/TS 候选为 `@tbc/kit@0.1.0-rc.23`，配套 Native 为
`0.1.0-rc.23.native.2`。协议指纹不变。当前 rc.22 交付、Flutter 合作方包
及冻结资源不替换；本轮无真实签名、广播、发布、推送或成功交易重放。

这些修复位于共享 Kit/Core/Engine，不是只修改验收 App。

## 已修复

| 问题 | 修复与保留边界 |
| --- | --- |
| NFT 手续费候选误占实际输入预算 | 创建集合、铸造、单笔转移、批量转移区分自动候选与实际输入角色；保留 256 候选边界、exact 预算、身份/金额/费用及 Engine 校验 |
| AMM 控制人顺序导致合法 3–5 人集合失败 | Engine 在请求哈希前规范化授权集合；Core 普通及 workflow 路径一致；重复、非法、空、超过 5 人仍拒绝；不重排收款人、交易顺序或多签公钥 |
| 业务错误显示内部失败/笼统冲突 | 规范化错误返回参数错误；普通 LP 不支持 lock/unlock 返回 `UNSUPPORTED_POOL_OPERATION`；NFT 指定槽已花费、身份不符、集合槽用尽均有固定原因 |
| LOP 代币路径同类预算误算 | make/cancel/match 的单个手续费角色不再按整组候选计数；原生币卖单/取消可能累积多输入，原有预算保留；exact 不丢弃输入 |
| Coin 管理、原生及代币 HTLC、LOP 已花费输出报错不清 | 只有有效的 `spent=true` 明确返回 `SELECTED_INPUT_SPENT`；缺失/非布尔状态继续拒绝，不伪装为已花费 |
| exact 不可用输入、输入/候选预算超限 | 补充固定原因码，不静默替换指定输入；不根据任意异常字符串猜测或对外暴露 Vault/API 内部文本 |
| 并行读取提前失败遗留 rejected Promise | NFT/Coin 管理观察未消费的 tip Promise；真正需要链高的路径仍等待原 Promise 并失败关闭，不吞掉必要校验 |

多收款人并非简单“8 人必定可用”：8 是输出组预算，还要为代币找零、TBC 找零和
附带付款留位置。本轮补齐说明，并实测 TBC20 有双找零时 6 人通过/7 人拒绝，
带普通付款时 5 人通过/6 人拒绝；不丢收款人、不吞找零、不擅自拆单。

## 性能口径

`evidence/installed-check.json` 记录 rc.22 与最终 rc.23 包的交替独立进程对照：
每边去掉首轮后取 4 次中位数；覆盖转账、合并、HTLC、挂单、加池、卖出和 LP 转移。
所有被测路径请求集合、交易字节、一次审批一致。

| 路径 | rc.22 中位 ms | rc.23 中位 ms | 请求数（不变） |
| --- | ---: | ---: | ---: |
| TBC20 转账 | 123.77 | 123.02 | 5 |
| TBC20 合并 | 64.46 | 63.76 | 5 |
| HTLC 锁定 | 58.65 | 58.45 | 6 |
| LOP 建单 | 58.56 | 57.33 | 5 |
| 加 LP | 211.59 | 209.37 | 9 |
| FT→TBC | 195.99 | 195.96 | 9 |
| LP 转移 | 103.58 | 102.61 | 7 |

上表来自最终归档的干净安装对照。源码模板 Native 锁同步前的相同可执行代码
对照范围是 −0.76～+3.79 ms，保存在 `evidence/code-frozen-installed-check.json`；
该轮归档哈希不同是溯源元数据的变化，不是交易代码变化。两轮都未发现明显回归，
不把末轮全部略快宣称为固定性能提升。

这是 Mac Node/WASM 的受控本地耗时，不是 iOS/Android 真机或公网端到端测速。
轻微毫秒级波动不能解释为产品固定加速/减速，不能据此保证所有设备零回归。
