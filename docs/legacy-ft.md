# 旧 FT 审批与指定输入

使用 [当前配套 JS 与 Native SDK](installation.md)，通过统一 `tbc20.transfer` / `tbc20.merge` 入口处理受支持的旧 FT。Kit 从认证材料识别合约，不根据代币名称判断协议。

## 审批展示

转账和合并计划的 `preview.assetFlows` 包含 `contractId`。钱包在批准前展示合约 ID、最小单位数量、收款人和费用，并保留逐笔 `outputReview`；这些是审批材料，不是广播回执。

复用 Kit 的审批绑定、validate 和 finalize。不得用 DApp 提供的标签替代合约身份，也不能在批准后编辑摘要或输入集合。

## 精确指定输入

`constraints.inputOutpoints` 是本次必须恰好消费一次的全部原始输入，包括 FT 输入和原生手续费输入，不是候选列表。每项为 `{ txid, vout }`。不传该字段时沿用自动选币。

- 列出所有选定的 FT 输入及手续费输入；Kit 不会静默补选未列出的外部输入。
- FT 转账超过单笔输入上限时，复用多轮合并计划；多个手续费输入复用资金归集前置交易。
- 前序交易生成的中间输出由依赖计划内部引用，不列入原始输入集合。
- 账户归属、合约身份、材料、确认政策、总手续费与交易数限制仍然生效。独立旧 FT merge 保持 2～5 个资产输入的范围。

数量使用最小单位十进制整数字符串。参数样例见 [随包使用手册](../packages/kit/docs/usage.md#historical-ft-approval-and-selected-inputs)；底层 `tbc.ft.transfer` / `tbc.ft.merge` 使用相同输入语义。

## 执行与升级

保持整批一次受限审批，复用并行预取与已准备材料，按原有依赖顺序签名、finalize 和提交，不需要新的取数接口。

新增的合约 ID 属于计划绑定内容。升级后重新准备尚未批准的计划，不通过改写已有审批材料进行迁移。已经广播或结果未知的交易仍按原交易标识核对，不因升级重新发送。
